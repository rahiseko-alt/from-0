# 放置台帳

## いつ書くか

`docs/test-policy.md` のGate（受け入れ基準）に対して、次の3パターンがある。

- Gateに触れない → 問題ない。書かない
- **Gateに触れたが、突き破ってはいない（ヒヤリハット）→ ここに書く**
- Gateを突き破った → その場で直す。放置しない（001〜080はRelease Gate上必須のため、
  放置自体ができない）

放置しても次に進めるか否かだけが書く・書かないの基準。最重要なのはゴールに進むことであり、
致命的でない限り立ち止まらない。

## 何を書くか

書きっぱなしでよい。自由記述で構わないが、次の3点は必須。

- **日時**（いつ触れたか。前後のコミット・PRから段階を辿れるようにする）
- **触れたGate番号・カテゴリ**（例: `023 データ整合性`）
- **対象箇所**（ファイル・機能など、どこを触れたか）

理由や「なぜ大丈夫と判断したか」は書かなくてよい。読み手に理由を信用させるのではなく、
「いつ・どこ」から読み手が実際にその箇所を確認しに行けるようにする設計。これは
`docs/test-policy.md` の Evidence Rule（`たぶん`・`理論上` を禁止し、証拠を要求する）と
同じ考え方。車で例えると、サイドミラーをぶつけただけならエンジンへの影響は疑わない。
ボンネットをぶつけて異音がしたなら足回りではなくエンジン周りを確認する、という発想。

`docs/test-policy.md` の Backlog Rule（Gate 081〜100 で見つけたが今回は直さない問題）も
ここに記録する。放置してもゴールできるという性質は同じであり、記録先を分ける理由がないため
統合している。

## いつ読むか

**大計画のゴール（問題がなければ即リリースできる状態）に到達したときだけ読む。**
リリース前の振り返りに使う。記録された日時・Gate・対象箇所を手がかりに、その箇所へ実際に
確認しに行き、「触れたが破らなかった」判断が今も成立しているかを検証する。それ以外の
タイミングでは読まない。詳細は `AGENTS.md`「失敗と放置の記録」を参照。
