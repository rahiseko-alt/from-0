# 全体計画をつくる

**このスキルは1つのプロジェクトにつき1回しか使いません。** すでに `docs/plan.json` が
あるなら、実行せずにその旨を報告して終わってください。

雛形（from-0）には `docs/plan.json` を同梱していません。**複製した直後は必ずここから始まります。**
`docs/plan.example.json` は形の見本で、計画そのものではありません（消さずに残しておいて構いません）。

## 計画に対してできること

- 各項目の `status` を変える
- **末尾に**新しい項目を追記する（番号は `pnpm run plan:next-id` が出す値）
- `dependsOn` / `files` / `verify` / `deliverable` / `verifyBy` を現実に合わせて**直す**

**してはいけないのは id を消す・使い回す・振り直すことだけです。** 過去のコミット・PR・
台帳からの参照が壊れるため。それ以外の欄は、現実とずれたら直してください（履歴は Git が持っています）。
やらないと決めた項目は**消さずに `status` を `dropped`** にします。

## 手順

### 1. ゴールを1文で決める

「問題がなければ即リリースできる状態」を書きます。ユーザーに確認してください。

### 2. 項目に分ける

**数を先に決めないでください。** 1項目の大きさは次で決まります。

> **1項目 = 1セッションで終わる大きさ = end-to-end の確かめ方を書ける大きさ**

一気に全部やろうとするとコンテキストが尽きて失敗します。逆に、差分を一文で説明できる
ほど小さいものは項目にする必要がありません。目安は初回で30〜50項目です。

**確かめ方が書けない項目は、粒度が大きすぎます。** 分けてください。

### 3. 各項目を JSON で書く

`docs/plan.example.json` と同じ形にします。項目ごとに次を埋めます。

| 欄              | 書くこと                                                               |
| --------------- | ---------------------------------------------------------------------- |
| `id`            | `T001` から連番。一度振ったら不変                                      |
| `title`         | 一言の名前                                                             |
| `deliverable`   | 完成すると何ができるか。依存する側がこれを読んで判断できるように書く   |
| `verify`        | 確かめ方。**人間が画面でたどれる操作の手順**として書く                 |
| `dependsOn`     | 依存する項目の id                                                      |
| `files`         | 触るファイル。**重複を隠さず全て挙げる**（作業範囲の関門がこれを見る） |
| `verifyBy`      | `ci` / `agent` / `human`（下記）                                       |
| `verifyCommand` | `verifyBy` が `ci` のときだけ必須。実際に走らせるコマンド              |
| `status`        | 最初は全て `todo`                                                      |
| `origin`        | 最初に作った項目は全て `initial`                                       |

**`verify` の書き方が最も重要です。**

```text
✗  「テストが通る」「正しく動作する」「エラーが出ない」
✓  「トップページの『会社概要』を押す」「戻るボタンでトップに戻れる」
✓  「自分宛に1通送る」「受信箱に届いていることを確認する」
```

**この書き方は機械で検査されます。** `docs/plan.json` を保存して `pnpm run test` を実行すると、
下の2つの条件を満たさない項目があるだけで検証が落ち、どの項目のどの手順が悪いかが出ます
（検査しているのは `src/plan.ts` の `validateVerifySteps`）。

- **手順1つは、前後の空白を除いて8文字以上**
- **その項目の確かめ方のどこかに「確認」「確かめ」「説明してもらう」のどれかの言葉が入っていること**

条件を満たすためだけに言葉を足しても意味がありません。検査は書き方の下限を見ているだけで、
**その手順を人間が本当にたどれるかどうかは機械には分かりません。**

#### `verifyBy` の決め方

**「その手順を誰が実行できるか」だけで決めます。**

| 値      | 意味                                     | 例                                                 |
| ------- | ---------------------------------------- | -------------------------------------------------- |
| `ci`    | コマンド1本で確かめられる                | 型検査、単体テスト、build                          |
| `agent` | 実物をなぞる必要があるが AI が実行できる | ファイルを開いて中身を読む、CLI を叩いて出力を見る |
| `human` | 実物を人間が見るしかない                 | 受信箱、印刷結果、住所や金額が正しいか             |

**「まだテストを書いていない」は `human` の理由になりません**（それは作業の進み具合であって、
項目の性質ではない）。逆に、**「Claude Code の機能だから機械側」も成り立ちません**。
そのコマンドを誰が入力するかまで下りて確かめてください（実際にここで間違えた例があります）。

`ci` を名乗るなら `verifyCommand` が必須です。**コマンドを書けないなら `ci` ではありません。**

### 4. 検証を通す

```bash
pnpm run test        # 書き方・id・依存先の存在
pnpm run plan:doctor # 循環依存・取り下げへの依存・行き止まり
```

両方通るまで直します。

### 5. 分解の漏れを、別の役に探させる（Goal Coverage Review）

**作った本人には、落としたものが見えません。** まっさらなサブエージェント（`Explore` など）に
次の指示だけを渡してください。

```text
ゴール: <goal の1文>

項目の一覧（title と deliverable だけ）:
  T001 ...
  T002 ...

この項目を全部やり終えたとき、上のゴールは本当に達成されますか。
達成に必要なのに、どの項目にも入っていないものだけを挙げてください。

見てはいけないもの: コード、git 履歴、status
挙げなくてよいもの: 粒度の good/bad、順番の好み、実装方針、命名
「不足なし」と判断したなら、その一言だけ返してください。
```

挙がったものは末尾に追記します（番号は `pnpm run plan:next-id`）。

### 6. ユーザーに見せる

**JSON をそのまま見せないでください。** 次の形に直して確認をとります。

```text
ゴール: 会社の紹介サイトが公開でき、問い合わせが届く状態

  T001  トップページの骨組み
        できるもの: ヘッダー・本文枠・フッターが並んだHTML 1枚
        確かめ方  : 開く → 幅を375pxまで狭める → 文字がはみ出していない
        依存      : なし

  ...（全項目）

  人が実物を見るしかない項目: 3件（T005, T012, T028）
```

聞くのは「**この順番と分け方で合っていますか**」だけです。
「この設計は妥当ですか」とは聞かないでください。
