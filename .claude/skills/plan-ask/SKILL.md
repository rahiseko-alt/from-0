# 確認をまとめて聞く

**人間に聞いてよいのは「これで合っていますか」だけです。**

## なぜ人間に聞くのか

AI と CI には、原理的に見えないものがあります。

```text
会社概要ページに、本社住所が「東京都◯◯区 1-2-3」と表示されている。

  AI  : 正しく表示されている。問題なし
  CI  : テスト通過。緑
  人間: 「そこ、去年引っ越した。今は違う住所」
```

**AI も CI も、これには永久に気づきません。** 料金が ¥3,000 のところ ¥300 でも同じです。
人間は検証の穴を埋める補助ではなく、**何が正しいかを唯一知っている人**です。

だから `verifyBy` が `human` の項目では、`adversary`（壊す役）を省きます。機械が壊せない
種類の間違いを見てもらう場所なので、機械的に壊しても意味がありません。

## いつ使うか

`status` が `awaiting_human` の項目が溜まったとき、または `pnpm run plan:state` が
`WAITING_HUMAN` を返したときです。1件ずつ呼び出さないでください。★は元々少ないので、
1件ごとに呼ぶと相手が続きません。溜めても、確認待ちの項目は `awaiting_human` のまま
完了に数えないので、進捗の数字が嘘になることはありません。

## 手順

### 1. 溜まっている項目を集める

`docs/plan.json` から `status` が `awaiting_human` の項目を全て取り出します。

### 2. 聞く前に、AI 側の準備を終えておく

人間に「確認してください」と言う前に、**確認できる状態を作っておきます。**
テストメールを実際に送る、画面を実際に開ける状態にする、など。
準備せずに聞くのは、作業を押し付けているだけです。

### 3. 1件ずつ、選択肢つきで聞く

**`AskUserQuestion` ツールを使ってください**（自由記述で聞かない）。順番は
「何が起きているか → どれを勧めるか → 選ぶとどうなるか → 選択肢」です。

```text
確認をお願いします（3件）

────────────────────────────────
1/3  問い合わせフォームの送信先

  やったこと : あなたのアドレス宛にテストメールを1通送りました
  見てほしい : 受信箱（迷惑メールフォルダも）
  質問       : 届いていますか？

  [ はい ]  [ いいえ ]  [ 届いたが内容がおかしい ]
────────────────────────────────
2/3  会社概要の中身

  やったこと : 打ち合わせでいただいた資料のとおりに入力しました
  見てほしい : http://localhost:3000/about.html
  質問       : 社名・住所・設立年は合っていますか？

  [ 合っている ]  [ 違うところがある ]
────────────────────────────────
```

**証拠は実物で示します。** スクリーンショット、実際の画面、届いたメール。
ログやテスト出力は見せないでください。

### 4. 答えを反映する

- **「はい」** → 判定を記録してから `status` を `verified` にする

  ```bash
  pnpm run plan:verdict T005 checker passed "本人に受信箱を見てもらい、届いていると回答を得た"
  ```

  （`verifyBy` が `human` の項目は `adversary` を省けます。関門もそれを前提にしています）

- **「いいえ」「おかしい」** → `status` は `awaiting_human` のまま。何がどう違うかを聞き、
  `pnpm run plan:next-id` で番号をもらって、末尾に直しの項目を追記する

- **「もうこの要件は要らない」** → `status` を `dropped` にし、`note` に取り下げた日と
  理由を書く。**`verified` にしないでください。** 取り下げを完了として数えると、
  やらないと決めたものが達成率を押し上げます（実際に3項目でこれが起きました）

## 聞いてはいけないこと

**これは確認ではなく、責任の押し付けです。**

```text
✗  T009 の実装が完了しました。nodemailer で SMTP 経由の送信処理を実装し、
   エラーハンドリングも追加しました。テストも通っています。確認をお願いします。
```

相手は「はい」と言うしかありません。何も検証されていません。

- **「このコードは正しいですか」と聞かない**
- **専門用語で状況を説明しない**（ライブラリ名、実装方式、テストの通過は相手の判断材料にならない）
- **YES/NO で答えられない聞き方をしない**
- **一度に全部並べて「確認してください」と丸投げしない**（1件ずつ、番号を振って聞く）
- **`docs/plan.json` をそのまま読ませない**（JSON は AI が書き換えにくいように選んだ形式で、
  読みやすさは犠牲にしている）
