# チェックアウト

作業を終えるときの締めです。

> **必ず `main` へのマージまで完了させてください。ただし対象は「引継ぎ文」です。**
> 次のセッションは `main` の `docs/handoff.md` しか自動では読まないため、引継ぎ文が
> 作業ブランチに残ったままだと次のセッションは気づけません。「PR を出した」で止めず、
> **引継ぎ文の PR** はマージまで進めてください。
>
> **実際のコード変更は、未完了なら push 済みの branch/worktree に残したままで構いません。**
> push していれば origin に残るため消えません（消えるのは push していないコミットだけ）。
> その場合は引継ぎの「次にやること」に、どの branch/worktree を見ればよいか明記してください。

## 手順

### 0. 独立した検証を受ける（`docs/plan.json` がある場合のみ）

**このセッションで作業した項目を、自分で `verified` にしないでください。** 通すのは
**2つの役**です。片方だけでは足りません。

1. **`completion-checker`** を呼び、`verify` の手順そのものをなぞらせる
2. `completion-checker` が「通った」を返したら、**次に**`adversary` を呼び、
   `deliverable` と `verify` を渡して壊させる（`verifyBy` が `human` の項目は省略可。
   実物は人間にしか見えないため、その層は `/plan-ask` に任せる）
3. 両方の結果を記録する

   ```bash
   pnpm run plan:verdict T011 checker  passed "<実行したコマンドと出力>"
   pnpm run plan:verdict T011 adversary passed "<試した手口と、破れなかった旨>"
   ```

4. `docs/plan.json` の `status` を書き換える

   | 判定                                     | 書く `status`                      |
   | ---------------------------------------- | ---------------------------------- |
   | checker が通り、adversary も破れなかった | `verified`                         |
   | checker が通り、`verifyBy` が `human`    | `awaiting_human`（`/plan-ask` へ） |
   | どちらかが通らなかった                   | `todo` のまま。直して0からやり直す |

**記録の無い `verified` は関門（`.claude/hooks/verified-guard.sh`）が止めます。** 先に
`pnpm run plan:verdict` を実行してから `status` を書き換えてください。

作った本人が採点者になると、「動いているように見える」が唯一の合図になります。
実際に、十分にテストせず完了マークを付ける失敗が観測されています。

**`completion-checker` に渡すのは `verify` の手順そのものです。** id だけ伝えて
`docs/plan.json` を読ませると、`status` が目に入ります。手順を本文に書き写して渡してください。
**`adversary` に渡すのは `deliverable` と `verify` だけです。** `status` も git 履歴も
「できました」報告も渡さないこと（`.claude/agents/adversary.md`）。

実行できない手順（ユーザーの操作が要るもの等）があれば、代わりに何を確かめるかを
指定し、**実行できなかったことを報告に明記させてください**。

### 0.5 全体照合を挟んだ場合

`pnpm run plan:state` が `GLOBAL_VERIFY_REQUIRED` を返してこの手順に来た場合は、
`/plan-verify` を先に実行してください。終わったら `docs/checkpoints.json` の
`globalVerifiedCount` を、そのときの「済」件数に更新します。

### 0.9 全項目が片付いた場合

`pnpm run plan:state` が `FINAL_VERIFY_REQUIRED` 以降を返したら、`/release` へ進みます。
**「次は何をしますか」とユーザーに聞かないでください。** 工程は決まっています。

### 1. 引継ぎを更新する

`docs/handoff.md` の4節を、次のセッションが**これだけ読めば再開できる**水準に書き換えます。
`<!-- session-end-stamp -->` 以降は自動記録なので触りません
（このマーカーは手元の `.claude/.session-end.md` を指すだけで、origin には残りません）。

- **いま何をしているか** — 目的と到達点。完了していれば「完了済み。次の作業は未着手」
- **完了したこと** — 変更したファイル、PR の番号とリンク、通した検証。実際に確認した事実だけ
- **次にやること** — 具体的な次の一手。判断待ちなら、誰の何の判断を待っているか。**複数
  branch が同時進行中なら、branch ごと1エントリで列挙する**（詳細はその branch の
  コミット/PR に置き、ここには短いポインタだけ）
- **注意点** — 踏んだ落とし穴、未解決の問題、**試して駄目だった方法**。**`AGENTS.md`/
  `docs/decisions.md` に既にある恒久的なルールは書かない**（食い違いの元になる）

確度の低い記述には `[曖昧]` を付けます。

作業範囲を固定したままセッションを終える場合は `pnpm run plan:stop` で解除してください
（次のセッションが別の項目を選んだときに、古い固定が残って混乱しないように）。

### 2. 検証を通す

```bash
pnpm run check
pnpm run build
```

**`main` へマージするもの**（引継ぎ文、または完了した作業）については、失敗したまま
締めないでください。直せない場合は、その事実と原因を引継ぎの「注意点」に書きます。
未完了のまま branch/worktree に残すコードは、この時点で通っていなくても構いません
（その旨を引継ぎに書いてください）。

### 3. コミットして push する

`main` への直接 push は Ruleset で禁止されています。作業ブランチへ push してください。
**作業が未完了なら、コードの変更はそのブランチに push したままで構いません。
無理に完成させる必要はありません。**

### 4. PR を出してマージする

- **作業が完了している場合** — 引継ぎの更新をその PR に含めてマージします
- **作業が未完了の場合** — コードの変更は PR にせず branch/worktree に残したまま、
  **引継ぎ文だけ** `main` へ向けた別 PR にしてマージします。引継ぎの「次にやること」に、
  どの branch/worktree を見ればよいか明記してください
- **調査だけで終わった場合** — 引継ぎ単体で PR を出してマージします

いずれの場合も、**main へ実際にマージする PR の CI** が緑になるのを待ち、
ドラフトなら解除してからマージします（未完了のコード側ブランチの CI は問いません）。

### 5. main に載ったことを確認する

```bash
git fetch origin main
git show origin/main:docs/handoff.md | head -30
```

**更新内容が `origin/main` 側に見えることを目視で確認してください。**

### 6. 消えるものを洗い出す

**セッションのコンテナは終了後に破棄されます。** origin に無いものは全て消えます。
思い込みで判断せず、実際に確認してください。

```bash
git status --short                        # コミットしていない変更
git log --branches --not --remotes --oneline   # push していないコミット
git stash list                            # stash に退避したもの
git worktree list                         # ローカルにしかない worktree
```

消えるもの／消えないものは次のとおりです。

| もの                                   | どうなるか                                                                            |
| -------------------------------------- | ------------------------------------------------------------------------------------- |
| `origin` に push 済みのブランチ        | **残る**（main にマージしていなくても消えない）                                       |
| push していないコミット                | **消える**                                                                            |
| コミットしていない作業ツリーの変更     | **消える**                                                                            |
| `git stash` の中身                     | **消える**                                                                            |
| `.claude/.verdict/` の判定記録         | **消える**（gitignore 済み。`docs/plan.json` の `status` に反映してあれば結論は残る） |
| `node_modules` / `dist` / 一時ファイル | 消えるが、作り直せるので問題ない                                                      |

**消えて困るものが残っていたら、この時点で push してください。** 未完成でも構いません。
push さえしていれば origin に残ります。

## 報告の形式

```text
引継ぎ: 更新済み / main にマージ済み（<コミットSHA>）
検証: check 通過 / build 通過
消失: <コンテナ破棄で失われるもの。無ければ「なし」>
残件: <次のセッションが引き継ぐこと。無ければ「なし」>
```

**「消失」は必ず書いてください。無いなら「なし」と明示します。** 書かないことと
「無い」ことは、読み手には区別がつきません。何かが消えるなら、それが何かを具体的に
書きます（「作業ツリーの未コミット変更3ファイル」など）。

マージできなかった場合は、**何が阻んでいるか**を明記してください。CI が赤い、コンフリクト、
必須チェックが未実行など、原因を特定して報告します。黙って終わらせないこと。
