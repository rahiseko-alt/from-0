# チェックイン

作業を始める前の点検です。**報告は「現在地」と「次の一手」だけ**にしてください。

## 手順

1. **いまの工程を確かめる**

   ```bash
   pnpm run plan:state
   ```

   **これが現在地の正本です。** 自分で「たぶん次はこれ」と決めないでください。
   SessionStart フックが同じ内容をセッション冒頭に差し込んでいるので、既に見えているはずです。

   返ってきた工程によって、この後の手順が変わります。

   | 工程                         | どうするか                                        |
   | ---------------------------- | ------------------------------------------------- |
   | `PLAN_REQUIRED`              | `/plan-init` へ。以降の手順は不要                 |
   | `BROKEN`                     | `pnpm run plan:doctor` を直す。それが今回の作業   |
   | `GLOBAL_VERIFY_REQUIRED`     | `/plan-verify` へ。それが今回の作業               |
   | `READY` / `WORKING`          | 手順2へ（通常の開発）                             |
   | `WAITING_HUMAN`              | `/plan-ask` へ                                    |
   | `BLOCKED`                    | 待ち先を確認し、ユーザーに報告                    |
   | `FINAL_VERIFY_REQUIRED` 以降 | `/release` へ。**「次は何をしますか」と聞かない** |

2. **main を同期する**

   ```bash
   git fetch origin main --prune
   git status --short
   git log --oneline origin/main -3
   ```

   ローカルが `origin/main` より古い場合は追いつかせます。作業ブランチが前回のマージで
   不要になっているなら、`origin/main` から作り直します。

3. **引継ぎを読む**

   `docs/handoff.md` は `AGENTS.md` から import されるため、すでにコンテキストにあります。
   ただし**それは前回セッション終了時点の内容**です。`origin/main` の最新版と食い違っていないか、
   ファイルを開いて確認してください。

4. **未処理の PR を確認する**

   オープンな PR があれば、CI の結果とマージ可否、未解決のレビューコメントを確認します。
   赤い CI やコンフリクトが残っていれば、それが最優先の作業です。

5. **次の1項目を選び、作業範囲を固定する**（工程が `READY` / `WORKING` のとき）

   **自分で選ばず、コマンドに選ばせます。**

   ```bash
   pnpm run plan:progress   # いまの進み具合
   pnpm run plan:next       # 次に着手する1件
   pnpm run plan:start T011 # 作業範囲を固定する（id は plan:next が出したもの）
   ```

   `pnpm run plan:start` を実行すると、その項目の `files` に無いファイルの編集が止まります。
   **範囲を広げたくなったら、先に `docs/plan.json` の `files` を直してから**もう一度実行します。

   `pnpm run plan:next` が出した1件が、このセッションのスコープです。
   **1セッションで扱うのは1項目だけです。**

   着手する前に、前回までの成果が**今も動くか**をざっと確かめてください。いきなり実装に
   入ると、既に壊れているものの上に積み増して問題を悪化させます。

6. **食い違いを検出する**

   引継ぎの「次にやること」が、すでに完了している／もう不要になっていることがあります。
   その場合は指摘してください。黙って古い計画を実行しないこと。

## 報告の形式

```text
現在地: <plan:state の工程と、いま何がどこまで進んでいるか。1〜2行>
未処理: <オープンな PR、赤い CI、コンフリクト。無ければ「なし」>
スコープ: <このセッションでどこまでやって終わりにするか。完了条件を1行で>
次の一手: <具体的に何をするか。1行>
```

引継ぎと実態が食い違っていた場合のみ、その差分を追記してください。

### スコープの決め方

**「終わったと判断できる線」を、着手前に引いてください。** 線を引かずに始めると、
どこまでやっても終わらず、コンテキストが尽きた時点で中途半端に切れます。

- `docs/plan.json` がある場合 — 選んだ1項目がそのままスコープです
- 無い場合 — ユーザーの依頼を「何ができたら終わりか」の形に言い換えます

```text
✗  スコープ: 認証まわりを改善する
✓  スコープ: ログイン画面でパスワード再設定リンクを押すとメールが届く状態まで
```

引継ぎを `main` にマージするところまでが `/checkout` です。マージしないまま
セッションが終わると、このセッションの成果は次のセッションから見えなくなります。

例外は次の2つだけです。この場合は `/checkout` せず、状況を報告して指示を仰ぎます。

- スコープの途中でユーザーの判断が必要になり、答えを待っている
- スコープを達成できないことが分かった（原因を明示すること）
