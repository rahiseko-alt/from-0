# 完成してから公開まで

**項目が全部終わることと、公開してよいことは別です。**

項目ごとの確認（`completion-checker` / `adversary`）は、その項目1つが `verify` のとおりに
動くかしか見ていません。**分解のときに落ちたもの**は、どの項目にも属さないので誰も見ません。
ここはそれを拾う最後の場所です。

## いつ使うか

`pnpm run plan:state` が次のいずれかを返したとき。**ユーザーに「次は何をしますか」と
聞かないでください。** 工程は決まっています。

```text
FINAL_VERIFY_REQUIRED    → 手順 1 から
NEGLECT_REVIEW_REQUIRED  → 手順 2 から
RELEASE_GATE_REQUIRED    → 手順 3 から
RELEASE_READY            → 手順 4 だけ
```

## 手順

### 1. 最終ゴール受入（実物がゴールを満たすか）

`docs/plan.json` の `goal` を読み、**完成した実物を端から端まで1回通してください。**
項目単位の `verify` はここでは見ません。見るのは「ゴールの文が本当になっているか」だけ。

- ゴールが「問い合わせが届く状態」なら、**実際にフォームから送って受信箱を見る**
- 途中で止まる・そもそも到達できない導線があれば、それは**分解の漏れ**です

漏れが見つかったら、直さずに項目として積みます。

```bash
pnpm run plan:next-id
```

`docs/plan.json` の末尾に `origin: "added"` で追記し、通常の開発ループに戻ります
（`/checkout` して、次のセッションで1項目として扱う）。**このセッションで直そうとしないこと。**

通ったら `docs/checkpoints.json` の `finalGoalAcceptanceAt` に日時を書きます。

```json
{
  "globalVerifiedCount": 28,
  "finalGoalAcceptanceAt": "2026-09-03T12:00:00Z",
  "neglectReviewAt": null
}
```

### 2. 見送った問題の見直し

`docs/neglected-log.md` を**全件**読みます。ここが唯一の読むタイミングです。

各エントリについて、記録された日時・Gate 番号・対象箇所を手がかりに、**その箇所へ実際に
確認しに行きます。**「触れたが破らなかった」判断が今も成立しているかだけを見ます。

- 今も成立している → 何もしない
- 成立していない → 手順1と同じく項目として積み、開発ループへ戻る

全件見終えたら `docs/checkpoints.json` の `neglectReviewAt` に日時を書きます。

### 3. 公開前の確認

`/release-review` を実行します。判定は `docs/release-review.json` に書き、可否は
`pnpm run release:check` が決めます。

**`FAIL` や `UNKNOWN` が 001〜080 に1件でもあれば公開できません。** 直してから戻ります。

### 4. ユーザーに聞く

`pnpm run plan:state` が `RELEASE_READY` になったら、**聞くのは1つだけ**です。

`AskUserQuestion` で、次の形にします。

- **何が起きているか** — 「作るものが全部できて、公開前の確認も通りました」
- **どれを勧めるか** — 「公開してよいと思います」
- **選ぶとどうなるか** — 「公開すると、誰でも見られる状態になります」
- **選択肢** — 「公開する」/「まだ公開しない」

**技術的な説明をしないでください。** Gate の番号も、テストの件数も、判定ファイルの中身も
相手の判断材料になりません。

## やらないこと

- **手順を飛ばさない。** 3 だけやって公開しない（分解の漏れも見送った問題も残ったままになる）
- **自分で「公開してよい」と宣言しない。** 判定は `pnpm run release:check` の出力
- **見つけた漏れをこのセッションで直さない。** 項目として積み、通常のループへ戻す
